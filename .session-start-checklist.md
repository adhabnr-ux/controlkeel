# Session Start Checklist - ControlKeel Governance

**Use this checklist at the start of EVERY session, regardless of host or context**

## Step 1: Load Governed State

- [ ] Call `ck_context` to load:
  - Mission and objectives
  - Budget status
  - Active findings
  - Proof state
  - Workspace context
  - Recent transcript events

**Why**: Conversation summaries are NOT substitutes for governed state. Each session needs fresh context.

## Step 2: Activate Governance Framework

- [ ] Invoke `controlkeel-governance` skill
- [ ] Review session risk tier (critical, high, medium, low)
- [ ] Review compliance requirements (HIPAA, HITECH, OWASP, etc.)
- [ ] Review active findings count and blocked count

**Why**: The governance skill enforces the core loop and provides safety rails.

## Step 3: Check Budget

- [ ] Call `ck_budget` to check:
  - Daily budget remaining
  - Session budget remaining
  - Rolling 24h spend

**Why**: Expensive operations (multi-phase work, large scans) require budget awareness.

## Step 4: Understand Task Context

- [ ] Is this a new task or continuing from a previous session?
- [ ] If continuing: TREAT AS NEW SESSION (invoke fresh governance)
- [ ] Review task requirements and constraints
- [ ] Identify if this requires ck_review_submit for plan approval

**Why**: Session resumption is the most common governance failure point.

## Step 5: Plan Validation (If Applicable)

- [ ] For complex tasks: Use `align` skill for shared understanding
- [ ] For multi-phase work: Use `plan-slice` for vertical decomposition
- [ ] Submit plans with `ck_review_submit` for approval
- [ ] Wait for approval before implementation

**Why**: Planning before implementation prevents expensive mistakes.

## Step 6: Create Session State File

- [ ] Create `.ck-session-governed` file with timestamp
- [ ] File content: `{"governed_at": "TIMESTAMP", "risk_tier": "TIER", "session_id": "ID"}`

**Why**: This enables git pre-commit hook to verify governance was completed.

## Step 7: Begin Work

- [ ] Only after completing steps 1-6
- [ ] Call `ck_validate` before any code/config/shell/deploy changes
- [ ] Use `ck_memory_record` for important decisions
- [ ] Use `ck_finding` for any issues discovered

**Why**: These are the ongoing governance protocols during implementation.

## Common Pitfalls to Avoid

❌ **Treating conversation summaries as governed state**
- Summaries are historical records, not live governed state
- Always call ck_context at session start

❌ **Skipping governance for "small" changes**
- Even small changes require governance in critical-risk sessions
- The risk tier determines governance requirements, not change size

❌ **Assuming "continuation" means "skip governance"**
- Every session is a new session from governance perspective
- Session resumption requires FRESH governance invocation

❌ **Relying on test passing as governance compliance**
- Tests passing ≠ policy compliance
- Tests passing ≠ budget respected
- Tests passing ≠ findings recorded

## Governance Failure Indicators

If you notice any of these, STOP and invoke governance:

- You haven't called ck_context in this session
- You're about to write code without ck_validate
- You're doing multi-phase work without budget check
- You're continuing from a summary without fresh governance
- You haven't created .ck-session-governed file

## Emergency Bypass (NOT RECOMMENDED)

If you absolutely must bypass governance (emergency only):

1. Document the emergency reason
2. Create .ck-session-governed file with emergency flag
3. Complete retrospective immediately after
4. Submit for review

**Note**: Emergency bypasses will be audited and may require explanation.
